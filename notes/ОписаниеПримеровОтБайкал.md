# Примеры HAL для BE-U1000 SDK 2.3.0

## Назначение

В каталоге:

```text
Projects/HAL_examples
```

находятся примеры работы с периферией микроконтроллера BE-U1000. Это не готовые прикладные программы, а небольшие эталонные проекты, которые показывают:

- как инициализировать конкретный периферийный блок;
- как настроить GPIO и BSP;
- как работать с прерываниями;
- как использовать DMA;
- как организовать обмен по UART, SPI, I2C, I2S и CAN FD;
- как работать с внутренней и внешней Flash;
- как использовать USB Device и USB Host;
- как работать с watchdog;
- как использовать CLIC, CLINT и несколько ядер;
- как запускать FreeRTOS.

Наиболее полезный подход при разработке собственного проекта — брать из примеров не весь проект целиком, а отдельные рабочие фрагменты:

```text
инициализация периферии
→ настройка тактирования
→ настройка GPIO
→ запуск
→ обработчик прерывания
→ чтение/передача данных
→ обработка ошибок
```

# 2. Типовой порядок работы с примером

Большинство примеров имеют собственный `Makefile`, а общая логика сборки находится в:

```text
Tools/build/common.mk
```

Пример проекта:

```text
Projects/HAL_examples/GPIO/GPIO_InputPollingBSP
```

Типовая сборка для EVU-BA 2.5 с запуском из TCM:

```powershell
make clean
make MEM_REG_ROM=TCMA BOARD=EVU_BA_2_5
```

После сборки результат обычно находится в:

```text
output/debug
```

Например:

```text
GPIO_InputPollingBSP.elf
GPIO_InputPollingBSP.bin
GPIO_InputPollingBSP.hex
GPIO_InputPollingBSP.disasm
GPIO_InputPollingBSP.lss
GPIO_InputPollingBSP.sym
GPIO_InputPollingBSP.map
```

Для загрузки в TCM через DFU используется бинарный файл:

```powershell
dfu-util --path 1-1 --alt 0 --download .\output\debug\GPIO_InputPollingBSP.bin
```

> `--path` необходимо брать из текущего вывода `dfu-util -l`. После переподключения USB номер устройства может измениться.

Режим `alt 0` соответствует:

```text
TCM and run
```

Программа запускается из TCM и исчезает после RESET или отключения питания.

# 3. GPIO

## 3.1. `GPIO_LEDBlink`

Минимальный пример работы с GPIO-выходом.

Основная идея:

```text
инициализация LED
→ изменение состояния GPIO
→ задержка
→ повтор
```

Типовой фрагмент:

```c
bsp_led_init();

for (;;) {
    bsp_led_toggle();
    __delay_ms(500UL);
}
```

Что демонстрирует:

- настройку пользовательского LED;
- работу GPIO как выхода;
- переключение состояния пина;
- простую блокирующую задержку.

Что можно использовать:

```c
bsp_led_init();
bsp_led_on();
bsp_led_off();
bsp_led_toggle();
```

Этот пример удобен как самый простой тест:

```text
МК запустился
→ LED мигает
→ GPIO и BSP работают
```

Исходник: [GPIO_LEDBlink][5]

---

## 3.2. `GPIO_InputPollingBSP`

Пример работы с пользовательской кнопкой и LED через BSP.

Основные функции:

```c
bsp_led_init();
bsp_btn_init();

uint8_t state = bsp_btn_ispressed();
```

BSP скрывает конкретные GPIO платы. Код приложения не обязан знать, на каком физическом выводе находятся кнопка и светодиод.

Простейшая реакция:

```c
if (bsp_btn_ispressed()) {
    bsp_led_on();
} else {
    bsp_led_off();
}
```

Определение фронта нажатия:

```c
uint8_t btn_state;
uint8_t btn_prev_state = 0;

for (;;) {
    btn_state = bsp_btn_ispressed();

    if ((btn_state == 1) && (btn_prev_state == 0)) {
        bsp_led_toggle();
    }

    btn_prev_state = btn_state;
}
```

Что демонстрирует:

- GPIO input;
- polling;
- BSP;
- определение изменения состояния кнопки.

Что можно использовать:

```text
bsp_btn_init()
bsp_btn_ispressed()
bsp_led_init()
bsp_led_on/off/toggle()
```

Исходник: [GPIO HAL examples][2]

---

## 3.3. `GPIO_InputPolling`

Похож на `GPIO_InputPollingBSP`, но полезен для понимания более низкого уровня HAL.

Подходит, если требуется:

- вручную выбрать GPIO;
- самостоятельно настроить направление;
- самостоятельно настроить pull-up/pull-down;
- читать конкретный GPIO без BSP.

Практический смысл:

```text
BSP-вариант
→ удобно для штатной платы

HAL-вариант
→ удобнее для собственной платы
```

---

## 3.4. `GPIO_InputIT`

Пример реакции на GPIO через interrupt.

В polling-варианте процессор постоянно делает:

```c
for (;;) {
    if (bsp_btn_ispressed()) {
        /* обработка */
    }
}
```

В interrupt-варианте основная программа может выполнять другую работу:

```c
for (;;) {
    process_uart();
    process_adc();
    update_state_machine();
}
```

а изменение состояния входа вызывает обработчик:

```c
void GPIO_IRQHandler(void)
{
    /* обработка события */
}
```

Пример показывает:

- настройку GPIO как источника IRQ;
- подключение IRQ к CLIC;
- обработчик прерывания;
- работу по фронту или уровню.

В Makefile можно выбирать тип события, например:

```powershell
make BTN_IT_TYPE=EDGE BTN_IT_MODE=BOTH
```

Возможные режимы включают:

```text
EDGE / LEVEL
ONE / BOTH
LOW / HIGH
```

Что можно использовать:

```text
настройка GPIO interrupt
CLIC configuration
ISR
очистка признака interrupt
```

Исходник: [GPIO_InputIT][3]

---

## 3.5. `GPIO_InputEXTI`

Показывает внешний interrupt через цепочку:

```text
GPIO
→ EXTI
→ CLIC
→ ISR
```

Подходит для:

- кнопок;
- внешних датчиков с линией `INT`;
- событий от другой микросхемы;
- сигналов, которые не нужно постоянно опрашивать.

Исходник: [GPIO_InputEXTI][4]

## 4.1. `UART_printf`

Показывает перенаправление стандартного:

```c
printf(...)
```

в UART.

Пример выводит строку:

```text
UART printf example
```

через UART0.

После интеграции такого механизма в собственный проект можно использовать:

```c
printf("button = %d\r\n", state);
printf("adc = %lu\r\n", adc_value);
printf("temperature = %.2f\r\n", temperature);
```

Это один из самых полезных инструментов при отладке.

Особое внимание следует обратить на:

```text
syscalls.c
```

Он связывает стандартную библиотеку C с конкретным устройством вывода.

Исходник: [UART_printf][7]

---

## 4.2. `UART_OneBoard_ComPolling`

Самый простой способ передачи и приёма.

Общая схема:

```text
CPU
→ проверяет UART
→ ждёт готовности
→ отправляет/принимает данные
```

Преимущества:

- простой код;
- удобно для первого запуска.

Недостатки:

- CPU блокируется ожиданием;
- плохо подходит для интенсивного обмена.

Что можно использовать:

```text
UART init
baudrate
TX
RX
проверка статуса
```

---

## 4.3. `UART_OneBoard_ComIT`

UART через interrupts.

Схема:

```text
UART получил байт
→ IRQ
→ ISR
→ обработка
```

CPU не обязан постоянно ждать UART.

Подходит для:

- командной консоли;
- Modbus-подобных протоколов;
- приёма небольших пакетов;
- фонового обмена.

Что можно использовать:

```text
UART IRQ enable
RX interrupt
TX interrupt
ISR
ring buffer
```

---

## 4.4. `UART_OneBoard_ComDMA`

UART с DMA.

Схема:

```text
RAM buffer
   ↓
 DMA
   ↓
UART
```

или:

```text
UART
   ↓
 DMA
   ↓
RAM buffer
```

Полезен для:

- больших пакетов;
- высокой скорости;
- снижения загрузки CPU.

Рекомендуемая последовательность изучения:

```text
Polling
  ↓
Interrupt
  ↓
DMA
```

Исходники: [ADC examples][8]

---

## 5.1. Как читать названия

Пример:

```text
ADC_ScanMode_Continuous_TriggerSW_DMA
```

расшифровывается так:

```text
ScanMode
→ несколько каналов

Continuous
→ измерения выполняются постоянно

TriggerSW
→ запуск программой

DMA
→ результаты автоматически складываются в память
```

---

## 5.2. Polling, Interrupt и DMA

### Polling

```text
CPU запускает ADC
→ ждёт
→ читает результат
```

Самый простой вариант.

### Interrupt

```text
CPU запускает ADC
→ продолжает работу
→ ADC завершает преобразование
→ IRQ
```

### DMA

```text
ADC
→ DMA
→ массив в RAM
```

Наиболее удобный вариант для непрерывного сбора данных.

---

## 5.3. Измерение внутренней температуры

Пример:

```text
ADC_ScanMode_Single_TriggerSW_Temperature
```

использует внутренний температурный канал микроконтроллера, периодически выполняет измерение и выводит результат через UART0.

Это хороший пример для первого запуска ADC, потому что внешний датчик не требуется.

Из него полезно взять:

```text
ADC init
→ start conversion
→ wait/read result
→ преобразование кода ADC в физическую величину
```

Исходник: [ADC Temperature][9]

## 6.1. `TIM_TimeBase`

Используется для генерации периодических событий.

Блокирующий вариант:

```c
bsp_led_on();
__delay_ms(1000UL);

bsp_led_off();
__delay_ms(1000UL);
```

во время задержки не позволяет основной логике нормально обрабатывать другие задачи.

Вариант с таймером:

```text
TIM
→ событие каждые N мс
→ обработчик
→ переключение LED
```

Основной цикл при этом остаётся свободным:

```c
for (;;) {
    read_button();
    process_uart();
    process_adc();
    update_state_machine();
}
```

Это важный шаг от учебного кода к нормальной embedded-архитектуре.

# 8. DMA

Примеры:

```text
DMA_MemoryToMemory_SRAM
DMA_MemoryToMemory_TCM
DMA_MemoryToPeriph
```

Исходники: [DMA examples][12]

DMA позволяет переносить данные без копирования каждого элемента процессором.

Вместо:

```c
for (i = 0; i < 4096; i++) {
    dst[i] = src[i];
}
```

можно настроить DMA:

```text
source address
destination address
transfer size
channel
direction
```

и запустить передачу.

После завершения DMA может вызвать interrupt.

Что полезно взять:

```text
DMA init
channel selection
source address
destination address
transfer size
IRQ on completion
```

DMA особенно полезен вместе с:

```text
UART
SPI
I2S
ADC
PWM
```

## 13.1. `USB_CDC`

BE-U1000 определяется компьютером как виртуальный COM-порт.

```text
BE-U1000
   │ USB
   ↓
Windows
   ↓
COMxx
```

Практическое применение:

- отладочная консоль;
- обмен командами;
- конфигуратор устройства;
- собственный текстовый или бинарный протокол.

---

## 13.2. `USB_HID_Keyboard`

Микроконтроллер представляется компьютеру как USB-клавиатура.

Пример возможного собственного приложения:

```text
User Button
→ HID report
→ Windows
→ нажатие клавиши
```

Полезно для изучения HID descriptors и USB reports.

---

## 13.3. `USB_MSC_TCM`

BE-U1000 становится USB Mass Storage Device, используя TCM.

```text
Windows
→ съёмный диск
```

Данные находятся в оперативной памяти и не сохраняются после перезапуска.

---

## 13.4. `USB_MSC_Flash`

Похожий пример, но хранилище организовано во Flash.

Полезен для изучения:

```text

block device
read/write callbacks
Flash storage
```

---

## 13.5. `USB_DFU`

Полезен для разработки собственного загрузчика и обновления прошивки по USB.

# 15. EFLASH

## Важно

Этот пример выполняет операции над внутренней eFlash и предназначен для тестирования памяти.

Он:

```text
стирает eFlash

→ читает данные обратно
```

Пример рекомендуется запускать из TCM.

> Не следует запускать `EFLASH_MemoryTest`, если во внутренней eFlash находится нужная прошивка или данные.

```text
erase
program
read
verify
```

```c
struct settings {
```

# 17. Watchdog

Пример:

```text
WDT_Reset
```

Watchdog используется для автоматического восстановления зависшего устройства.

Типовая схема:

```c
wdt_init();

for (;;) {
    do_work();

    if (everything_ok) {
        wdt_refresh();
    }
}
```

Если программа перестанет выполнять:

```c
wdt_refresh();
```

произойдёт:

```text
watchdog timeout
→ RESET
```

В README примера отдельно отмечается, что после перезапуска watchdog необходимо учитывать его состояние.

Что полезно взять:

```text
WDT init
timeout
refresh
reset behavior
```

Исходник: [WDT_Reset][20]

## 18.1. Vectored interrupts

Показывает переход непосредственно к обработчику конкретного interrupt.

Полезно для понимания:

```text

→ CLIC
```

---

## 18.2. Nested interrupts

Показывает вложенные прерывания.

Например:

```text
низкоприоритетный IRQ
        ↓
      ISR A
        ↓
приходит более высокий IRQ
        ↓
      ISR B
        ↓
возврат в ISR A
```

Это важно для систем с разными требованиями по времени реакции.

## 20.1. `FreeRTOS_Single_Core`

Демонстрирует несколько задач с разными приоритетами.

В примере используются задачи:

```text
Tx
Rx
Sem
```

Между задачами используется:

```text
queue
binary semaphore
```

Также применяется:

```text
heap_4.c
```

Пример показывает переход от монолитного цикла:

```c
for (;;) {
    button();
    uart();
    adc();
    usb();
    led();
}
```

к разделению функций на задачи:

```text
ButtonTask
SensorTask
CommunicationTask
LedTask
```

Типовая связь:

```text
SensorTask
    ↓ queue
CommunicationTask
```

или:

```text
ISR
 ↓ semaphore
WorkerTask
```

Исходник: [FreeRTOS_Single_Core][24]

В примере:

```text

→ core 0

Rx
Sem
→ core 1
```

Используются:

```text
tasks
queues
binary semaphores
core affinity
```

Этот пример имеет смысл изучать после обычного `FreeRTOS_Single_Core`.

Исходник: [FreeRTOS_SMP][25]

# 27. Основной принцип работы с HAL examples

При добавлении новой периферии в собственный проект удобно действовать по схеме:

```text
1. Найти ближайший HAL example
2. Собрать его без изменений
3. Проверить, что пример работает на плате
4. Найти минимальный блок инициализации
5. Понять используемые GPIO и тактирование
6. Перенести код в свой проект
7. Проверить peripheral отдельно
8. Только после этого объединять с остальными модулями
```

Такой подход уменьшает количество одновременно неизвестных проблем:

```text
не работает GPIO?
не работает clock?
неверный interrupt?
неправильный DMA?
ошибка в приложении?
```

Сначала проверяется официальная минимальная конфигурация, затем к ней постепенно добавляется прикладная логика.
